# Vision Superexpert KB - orchestration plan (loop-drive compiled)

## 1. What this file is

This is the loop-drive orchestration plan compiled from `2026-09-21.vision-superexpert-kb-plan.md` (the source plan, in this same directory).
One frontier-model session drives it: it runs the waves, launches workers, reads verdicts, gates, merges, and stops for the human only where this file says to.
The source plan remains the manual fallback: if the loop dies, a human can execute the source plan's tasks by hand in dependency order.
The source plan is ground truth for scope and acceptance; this file only says how to run it, never what to build.
Nothing here overrides a source-plan acceptance check; every unit is judged by the source plan's own verbatim `[executed-check]`.

Route: multi-wave dependent build.
Waves: `[T1] -> [T2, T3] -> [T4] -> [T5, T6] -> [T7] -> [T8]`.
Tracker: github, tracking issue #1 (`https://github.com/jroethel/vision/issues/1`).
Autonomy knob: auto (session override); every STOP below stays absolute regardless.

## 3. Orchestration shape and validation layers

Three tiers, unchanged across transports:

- Orchestrator (this session): the wave loop, gates, merges, spec edits, escalation, and the human checkpoints. Never implements. Reads logs, verdicts, and core diffs only.
- Validator (fresh per unit): for ringer units, the verbatim executed check consumed at the gate (plus an optional review task); for T7, a fresh-context Opus subagent. Adversarial, evidence-first, never fixes.
- Implementer (one worker per unit): a ringer manifest task (T1-T6, T8) or a background-agent subagent (T7). Test-first against the unit's criteria.

Three validation layers per unit: (1) the implementer's own self-check before it returns; (2) the per-unit validator (executed check, or the T7 subagent); (3) the orchestrator gate, which re-reads the raw evidence and merges only a green integration branch.

Topology (text sketch, not a rendered export):

```
orchestrator (this session, the loop)
  |
  wave 1  ringer manifest ....... [T1]              --> gate
  |
  wave 2  ringer manifest ....... [T2, T3]          --> gate      (disjoint files)
  |
  wave 3  ringer manifest ....... [T4]              --> gate      (full-corpus pass)
  |
  wave 4  ringer manifest ....... [T5, T6]          --> gate      (disjoint files)
  |
  wave 5  background agent ...... [T7] + validator  --> gate + HUMAN CHECKPOINT (recipe paste)
  |
  wave 6  ringer manifest ....... [T8]              --> gate + HUMAN [judgment] + terminal /loop-review
```

The dependency graph forces all six waves (T1 blocks all; T4 must be its own all-family pass; T7 needs T5's index; T8 needs T7); none can be collapsed under W-scaling.

## 4. Hazard mitigations

Each is marked as a deviation from the source plan where it is one.

1. Check custody (both transports).
   Every acceptance check is shipped verbatim in the source plan (`check_corpus.py`, `check_feeds.py`, `check_messages.py`, `check_retrieval.py`, `check_traversal.py`, `test_grow.sh`, and T7's inline skill-validity + headless smoke).
   The implementer transcribes its check verbatim; the validator confirms the on-disk check matches the source plan byte-for-byte before trusting a pass (a weakened check is an automatic scope violation, not a gate discussion).
   Judge map, and the rule that no unit may edit a check that judges it:
   - `check_corpus.py`: created by T1; judges T1, T2, T3 (imported), T4. T2-T6, T8 must not edit it.
   - `check_feeds.py`: created by T2; judges T2, T4. T4 must not edit it.
   - `check_messages.py`: created by T3; judges T3, T4. T4 must not edit it.
   - `check_retrieval.py`: created by T5; judges T5.
   - `check_traversal.py`: created by T6; judges T6.
   - `test_grow.sh`: created by T8; judges T8.
   - T7 skill-validity + headless smoke: run by T7's validator; embedded verbatim.
   T1 creating and being judged by `check_corpus.py` is allowed because the check is verbatim-pinned; the validator's byte-for-byte match closes the self-judging gap.
   (Deviation: the "no downstream unit edits a check that judges it" ownership constraint is added on top of the source plan's file-ownership lists.)

2. Ringer git-commit block (DEVIATION, every ringer unit T1-T6, T8).
   The source plan ends each task with `git add ... && git commit -m ...`.
   Ringer's lint hard-blocks any `git commit` inside a worktree, so those commit lines cannot be given to a ringer worker verbatim.
   Convert: the worker leaves changes uncommitted; its check exports the diff with `git add -A && git diff --cached > <workdir>/<unit>.patch`; the orchestrator applies the reviewed patch and commits on the integration branch at the gate, using the source plan's commit message.

3. Ringer deliverable loss (carried from `ringer-substrate.md`).
   A passing task's worktree is deleted and worker commits die with it.
   Corpus markdown and code are text, so the patch export in (2) carries them; the unit's resume pointer (`docs/handoffs/2026-09-21.<unit-slug>.resume.md`) is written into the worktree and must be included in the exported patch so the orchestrator commits it with the unit.
   Logs survive in `<workdir>/logs/`.
   opencode spawn staggering does not apply: the engine is claude-zai (GLM), not opencode.

4. T6 -> T1 -> T4 re-open ordering hazard (already noted in the source plan; carried here as an escalation path).
   If `check_traversal.py` classifies any of the ~3 known clObject drops as FIXABLE (anchor exists in the frozen source but was not rewritten), the fix lives in `common.py` (`rewrite_links` / `register_anchor`), which is T1's ownership.
   Editing `common.py` in T6 re-opens the T1 contract and invalidates T4's corpus.
   Resolution: T6 does not edit `common.py`; it records the fixable-drop finding as a spec/design issue routed to the orchestrator (stopped-unit style). The orchestrator makes the `common.py` edit as a T1 spec edit, re-runs T2, T3, T4 (rebuild), then re-runs T6.
   DANGLING-at-source drops are recorded, not failed, and trigger nothing.

5. qmd collection path durability across worktree pruning (DEVIATION / addition).
   `index.sh` registers the `vision` collection by absolute path (`$ROOT/corpus`), and the machine-global qmd cache lives in `$HOME`, shared across worktrees.
   A ringer worker that indexes its worktree's corpus leaves the collection pointing at a path that is deleted when the worktree is pruned.
   Mitigation: before any wave that queries qmd against the durable repo (wave 5's T7 smoke, wave 6's T8), the orchestrator runs `bash scripts/index.sh` from the integration-branch checkout so the collection points at the committed corpus at the stable repo path.
   `ensure-index.sh` is idempotent and self-heals this on the summon path.

6. T7 headless smoke worktree path (DEVIATION).
   The source plan's smoke begins `cd ~/create/vision`, which escapes a background-agent worktree and would test the main checkout's skill, not the worktree's new SKILL.md.
   The T7 worker must run the smoke from its worktree root (substitute the worktree path for `~/create/vision`); the orchestrator additionally re-runs the smoke post-merge on the integration branch at the gate.

7. Disjoint files within waves (confirmed; the source plan already converted shared append-only state to per-family checks and disjoint output dirs).
   Wave 2: T2 owns `feeds.py`, `check_feeds.py`, `corpus/feeds`, `corpus/reports`, `corpus/status`; T3 owns `classes.py`, `messages.py`, `check_messages.py`, `corpus/classes`, `corpus/messages`. Disjoint; both read T1's files and call `run.py --only` read-only.
   Wave 4: T5 owns `index.sh`, `ensure-index.sh`, `check_retrieval.py`; T6 owns `check_traversal.py`. Disjoint; T6 reads corpus files only and does not touch the qmd index.
   A merge conflict at a gate is a scope violation, not something to quietly resolve.

8. T4 full-corpus rewrite (by design, not a conflict).
   T4 re-writes the units T2 and T3 committed from their partial `--only` runs, because only the no-`--only` pass resolves cross-family links.
   This is safe because T4 is its own wave, with no concurrent writer to `corpus/`.

9. Dirty-tree STOP (absolute; autonomy never auto-resolves it).
   Worktrees branch from committed HEAD only. See pre-flight item in Section 5.

10. Per-unit logs.
    Ringer writes per-task logs to `<workdir>/logs/` automatically; the T7 background-agent unit log is `docs/loop/logs/vision-superexpert-kb/unit-07.md`.
    No source-plan shared append-only log file exists to convert.

## 6. Wave loop and gates

Per wave:

1. Launch.
   Ringer waves (1, 2, 3, 4, 6): emit one manifest for the wave with `run_name: vision-superexpert-kb` (the SAME across every wave), `workdir` under a loop work dir, `worktrees: true`, `max_parallel: 2`; run `./ringer.py lint <manifest> && ./ringer.py run <manifest>`. Ringer's built-in single retry IS the repair pass; do not add one.
   Background-agent wave (5): the harness runs T7 as a background worker and notifies on completion; on completion launch T7's Opus validator; on a failed validation, one repair pass steered to the same implementer, then revalidate; a second failure stops the unit.

2. Gate (orchestrator).
   Read all results and verdicts.
   Ringer: consume the run JSON in `~/.ringer/runs/` (statuses, retries, durations); the run JSON is truth, a background shell's exit status is transport. Read every retried or failed worker log in `<workdir>/logs/`, and spot-check at least one passing artifact.
   On a FAIL, attribute by a fresh re-run of the check against the tree, never by citing an earlier gate's verdict. If the worker's output was correct and the CHECK was wrong, fix the check, commit the audited work, and annotate the model log; otherwise relaunch.
   Apply reviewed patches to the integration branch (ringer units, per hazard 2), or merge T7's validated branch; then run the affected checks on the integration branch and advance only when green.
   Before wave 5 and wave 6, re-run `bash scripts/index.sh` from the integration checkout (hazard 5).
   Write the wave summary; ringer prunes its own worktrees; prune any others.

3. Distill before advancing.
   Turn any repeated failure pattern into a fix in the spec artifact and the templates before the next wave.
   Leave the dated MODEL-NOTES receipt for the wave's (model, task_type) in `<ringer-repo>/docs/MODEL-NOTES.md`, plus a separate line for any signal event (a pin, a re-route, a check-bug attribution, an off-nominal result); commit it in the ringer repo before advancing the wave.

4. Advance only on a green integration branch.

Gate classes under the auto knob:

- A spec edit confined to a single unit or criterion, leaving that unit's produced contract unchanged, touching 15 or fewer lines, auto-takes as BATCH and is journaled.
- A larger edit, or one touching multiple units, a global constraint, or a unit's produced contract, is a STOP and asks the human.
- Under auto, the pre-launch detail menu (Step 7) is not fired; the launch auto-takes and is journaled. The BATCH/DEFAULT auto-takes never dissolve a STOP.

Absolute STOPs (auto never auto-resolves any of these):

- Pre-flight dirty tree (Section 5 item 3).
- Any request to exceed the effort cap of high.
- Any outward-facing unit: T7's recipe paste touches `~/.config/just/justfile` (outside the repo, user-owned).
- Quota exhaustion mid-run or mid-attribution: halt, state what is needed, and the fresh check is still owed on resume.

Ask-the-human list:

- Pre-flight: the dirty-tree decision.
- Wave 5 gate: T7 HUMAN CHECKPOINT. Hand the user `scripts/vision-recipe.snippet` (both the `vision` and `vision-auto` recipes) to paste into `~/.config/just/justfile`; the user runs `just -g vision` and confirms the session boots in the repo with the `vision-expert` skill active and the index ensured. No executor edits `~/.config/just/justfile`.
- Wave 6 gate: the brief's one `[judgment]` criterion. The summoned expert completes one real co-primary task using only the knowledge base (author or correct a feed field mapping, or design an entity subclass with the right superclass and property kinds), and a human judges the result against live source or the ivr testkit.
- Any absolute STOP above.

Slip rules: a small spec issue at a gate means edit the spec artifact and relaunch that unit; a design issue is recorded for the plan's downstream review step (the same rule carries the T6 -> T1 -> T4 re-open of hazard 4, and any Spec-axis finding from the terminal review).

Final-wave terminal review: after wave 6's integration branch is green and the run advances, run `/loop-review <pre-run-base>` from the integration branch. It is advisory and non-blocking (the per-unit checks already gated correctness); record its findings at the final human checkpoint, and slip any Spec-axis finding to the downstream review step under the slip rules.
