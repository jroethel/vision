# Brief: a Vision knowledge base from docs/, phase 1 (ingest + access)

Date: 2026-09-21
Status: revised (supersedes the 2026-09-20 draft - that draft was a seed, not settled truth)
Stage: brainstorm output, next stage is /loop-plan

## Outcome

Turn the `docs/` directory into a knowledge base that makes the agent an expert Vision schema architect and data engineer, so schema and data-feed work is grounded in the real system instead of guessed.
The named mechanisms in the request (knowledge base, database, knowledge graph, index, embeddings) were hypotheses about how, not the outcome.
Presupposition verdict: the request assumed the missing piece is a retrieval or graph mechanism to build.
Verified this session, that assumption is mostly wrong.
Retrieval is already solved by an installed, tested tool (qmd, hybrid BM25 + vector + rerank), and the relationship graph is already written into the docs as hyperlinks and named anchors that survive conversion.
So phase 1 is not "build a mechanism" but "convert the docs into a clean corpus the existing tools can already work over, and prove one real task on it."
Phase 1 delivers the retrieve half of "retrieve and accumulate" - the accumulate half is designed-ready but built later (see Parking lot and Out of scope).

## End artifact

This is enabling work, so it must name the first real deliverable it unblocks.
First deliverable: the agent correctly performs one real co-primary task grounded in the KB, for example authoring or correcting a data feed's field mapping, or designing an entity subclass with the right superclass and property kinds, with the answer checkable against the source code or the ivr testkit rather than against the dated docs.
If the KB cannot yet support one such task end to end, phase 1 is not done.

## Done looks like

The agent can answer, over the derived corpus and never the raw HTML, which feed sets a given field and what its type is, for any of the co-primary feeds.
The agent can walk a schema relationship (a feed to a related feed, or a class to a message it inherits) by following the corpus's own preserved links, without loading unrelated files.
No single unit the agent must load to answer one question is large enough to threaten a working session.
Every derived unit points back to the frozen source it came from, so any claim is traceable.
Usage at task time is a query against the local qmd index (`qmd query "..."` or `qmd search "..."`) plus the agent's native read and link-following over the returned units, with no persistent service running.

## Approach

Chosen: convert the frozen docs to a clean markdown corpus with pandoc, shred only the oversized message files at their existing named anchors, stamp each unit with a provenance pointer to its frozen source, and access it through the already-installed qmd hybrid search plus link-following over the preserved cross-references.
Nothing new is built for retrieval or for the graph - both already exist and were verified this session.
The docs stay a dated seed while the live source and ivr testkit are ground truth, so on any doc-versus-code conflict the code wins.

This shape rests on three findings verified this session (2026-09-21), not on the prior draft:
- qmd indexed a 12-doc sample (242 chunks) in seconds and returned the correct unit with file:line provenance for exact-token, conceptual, and semantic queries, so hybrid retrieval keeps exact matching (BM25) while adding semantic recall.
- The relationship graph is already in the docs: all 330 named anchors in mObject survive pandoc as link targets, and 47 of 50 of clObject's deep-links into those anchors survive, so a class-to-message walk resolves inside the converted corpus with no separate graph store.
- pandoc renders the pma_ feed tables (including the grouped Required/Suggested/Other header rows) and the message files into clean markdown that qmd indexes directly.

Alternative considered, an LLM-extraction knowledge graph (Cognee, CocoIndex, LightRAG, OG-RAG): declined.
Dated research this session found each builds its graph by LLM extraction and would re-synthesize the relationships the docs already state as hyperlinks, at the cost of a graph database, an LLM key, and the risk of contradicting the authoritative links (Cognee v1.6.0 2026-09-18, CocoIndex V1 2026, LightRAG active 2026, OG-RAG a 2025 research reference).
For a small, fixed, already-cross-linked corpus this is cost without a matching gap.

Alternative considered, a materialized deterministic graph from the links (graphify, `uv tool install graphifyy`, or a small href-extraction script): parked, not chosen for phase 1.
It is the right tool only if one-hop link-following proves insufficient for reverse-edge or multi-hop queries that BM25 cannot answer - graphify's deterministic markdown-link path is documented but unverified against this dirty HTML, so it needs a 5-to-10-file test before adoption.

Alternative considered, native grep and read with no index at all (the prior draft's choice): rejected.
It throws away the semantic first-hop and the ranking that qmd already provides for free, and its stated reason for declining semantic retrieval (near-miss corrupts a schema, vectors lose provenance) does not hold, because qmd runs BM25 inside the hybrid and carries file:line provenance on every hit.

## Success criteria

Every co-primary feed and class/message reference in scope is represented in the derived corpus, checkable by count against the source. `[executed-check]`
For a chosen field name, retrieval over the corpus returns the feed that sets it and its type, with no false positive from a near-miss name. `[executed-check]`
A known class-to-message or feed-to-feed relationship can be followed entirely within the corpus by resolving preserved links, reading only the units on the chain. `[executed-check]`
No derived unit needed to answer a single question exceeds an agreed per-unit token budget. `[executed-check]`
Every derived unit carries a pointer to its frozen source. `[executed-check]`
The agent completes one real co-primary task (the End artifact) using only the KB, and the result checks out against code or the ivr testkit. `[judgment]`

## Seams

Independently checkable pieces, in blast-radius order:

1. Ingest: convert docs to the markdown corpus, shred the oversized message files at their anchors, stamp provenance.
   Highest blast radius because access and traversal both inherit its output and a bad ingest cannot be repaired cheaply.
   Check: the corpus exists, counts match the source, each unit traces to its origin, no unit exceeds the budget.
2. Access: index the corpus with qmd and confirm retrieval answers a real feed or schema question over budget-sized units.
   Check: a sample field-to-feed question returns the right unit, ranked, with provenance, reading no raw HTML.
3. Traversal: confirm the preserved cross-references resolve within the corpus.
   Check: a known class-to-message deep-link chain is followable entirely inside the converted units.

Piece 1 is a prerequisite to 2 and 3 - pieces 2 and 3 verify separately.

## Known vs guessed

Verified this session (2026-09-21):
211 .htm in docs/original/, 66 pma_ (38 with Field/Type/Description feed tables carrying grouped header rows, 27 with application-input specs, some both), 24 cl_, and the m_ message files.
mObject.htm converts to 5,370 lines / 164KB of markdown with all 330 named anchors preserved as link targets.
clObject's 50 deep-links into those anchors survive conversion at 47 of 50.
qmd 2.5.3 is installed and indexed a 12-doc sample into 242 chunks, returning correct provenance-bearing hits for exact, conceptual, and semantic queries.
pandoc and the other base tools (rg, sqlite3, uv, jq, python3, node) are present - graphify, Cognee, CocoIndex, and a vector DB are not installed.
The working tree shows ProcessUpdates.csh modified, a live signal that ops docs may already lag the code.

Believed-unchecked:
that the other 27 m_ files follow mObject's anchor-per-message structure, since only mObject was confirmed.
that the 3-of-50 dropped deep-links are a benign pandoc edge case (likely trailing-colon anchors) rather than a systemic loss.
that the ivr testkit can serve as a verifier for schema and feed claims, seen running but not exercised for this.
that most of the ~100 images are chrome rather than content, sampled not audited.

Guessed:
that one-hop link-following plus BM25 reverse lookup covers the traversal need without a materialized graph - if wrong, the fix is graphify or a small href-to-adjacency script, additive and reversible, not a change to the corpus.
that a single pandoc pass handles the dirty HTML per family cleanly - if wrong, ingest needs per-family parse rules, which changes ingest effort but not the chosen shape.

## Parking lot

- Design the grow loop and its per-role trust and autonomy model.
  Restart context: user chose to decide grow per-role later - the substrate is grow-ready because appended note files land in the same qmd collection and `qmd context add` attaches summaries, so accumulation needs no new mechanism - trust tiers stay provisional and code/test-anchored, with engineer accumulation cheap via reject files, architect accumulation advisory because schema commits are DBA-only, and sysadmin accumulation the fastest-drifting with the weakest test anchor.
- Extend the KB to the sysadmin role.
  Restart context: secondary role - sources are nix-build.md, adm_ pages, Running.htm, update-malloc-debugging.md, docs/VdbScan/, docs/year-end/ - most are already markdown so ingest is light - this knowledge drifts fastest because the .csh scripts are live and has the weakest ivr coverage.
- Materialize the cross-reference graph if link-following underperforms.
  Restart context: build a deterministic adjacency from the preserved hrefs and anchors via graphify (`uv tool install graphifyy`, no server, no vector store, no LLM) or a small script - test graphify on 5 to 10 real .htm files first because its markdown-link path is documented but unverified on this HTML and href extraction may route through an optional semantic backend.
- Build the codebase-sync staleness check.
  Restart context: a build-time check that diffs software/src/ and application/production/scripts/ since the KB's last sync and flags units describing changed areas as possibly stale - ProcessUpdates.csh is currently modified as a live example.
- Graph the C++ kernel for the code-anchored verifier.
  Restart context: deferred code phase - code-graph-mcp (SQLite + BM25 + sqlite-vec, local, no server) is the lighter candidate, but tree-sitter may struggle with a macro-heavy kernel, so test extraction fidelity on a sample before relying on it.
- Capture the real diagram images as cached text.
  Restart context: ~100 images in docs/original/, most chrome but the concept and tutorial diagrams carry real content - describe once at ingest and cache beside the doc, never analyze per session.

## Out of scope

The grow and accumulation loop, deferred by decision, with the substrate built ready for it.
The sysadmin role, held for phase 2.
Any LLM-extraction knowledge graph, external graph database, or vector store beyond qmd's own local index.
The Jekyll publish layer, which renders the docs as a website and is not KB content.
Editing the frozen docs/original/ files, which stay a faithful dated snapshot while the corpus is derived alongside them.

## Open questions for planning

- The shred granularity for the m_ files (per-message unit versus small message groups) - the 330 anchors and the cl_ deep-links already mark the boundaries.
- The provenance frontmatter schema for a corpus unit.
- Per-family pandoc parse rules and how to recover the 3-of-50 dropped anchor links.
- The per-unit token budget and how to enforce it at shred time.
- Where the derived corpus physically lives relative to docs/original/, and whether the corpus is committed while the qmd index is a gitignored build artifact.
- Whether ingest is a committed one-shot or a repeatable build step (`qmd update`).
- How the pma_ "id of existing X instance" rows are represented so both the feed record and the link graph carry them.
